# Policy pages: sidebar table of contents

Plan only, 30 Sep 2026. Nothing built.

Pages: Terms, Privacy, Refund, Contact, and Legal notice once it exists. Wanted: a sidebar list of
the headings, each linking to its section; sticky on desktop, collapsible on mobile; on the Walterin
design system; EN + SK. Reference: mywaynd.com/cookies.

---

## The constraint, established first

**A theme cannot template `/policies/...` pages.** `policy` is not in Shopify's list of valid
template types — there is no `templates/policy.json`, no `templates/policy.liquid`, no
`main-policy` section, and none has ever existed in Online Store 2.0.
Source: <https://shopify.dev/docs/storefronts/themes/architecture/templates>

Verified on the live page rather than taken from docs. `GET https://walterin.com/policies/terms-of-service`
returns, inside `<main id="MainContent">`, markup with **no `shopify-section` wrappers at all**:

```html
<div class="shopify-policy__container">
  <div class="shopify-policy__title"><h1>Terms of service</h1></div>
  <div class="shopify-policy__body"><div class="rte">…policy body…</div></div>
</div>
```

No sections, no blocks, no theme-editor presence. Three CSS hooks and nothing else. Liquid does not
run inside the policy body either.

**What we do have:**

- `layout/theme.liquid` runs normally on these pages — header, footer and `walterin-ui.css` all load.
- `request.page_type == 'policy'`, and the body tag is already `gradient wui t-policy cart-empty`
  (`layout/theme.liquid:342`). A reliable gate, for free.
- `shop.terms_of_service.body`, `shop.privacy_policy.body` etc. are readable from any other template
  — the policy text can be rendered elsewhere without copying it.
- Heading `id`s survive the Admin API: our own `id="legal-guarantee"` went into Terms clause 10 on
  29 Sep and is live. Inline `style=` survives too. `<script>` and web components are stripped.

**And one thing worth knowing on its own:** every page-frame rule in `assets/walterin-ui.css`
(lines ~130–163) is gated on `.wui:is(.t-product, .t-page)`. A policy page is `.t-policy`, so
**none of them apply**. The design system is loaded on these pages and is doing nothing. They are
laid out by Shopify's default container. That is why they don't look like the rest of the site,
and it is fixable independently of the table of contents.

## Options

### Option A — client-side ToC, injected from `theme.liquid`, gated on `t-policy` (recommended)

A snippet rendered only when `request.page_type == 'policy'`. On load it walks
`.shopify-policy__body .rte h2` (and `h3` if wanted), gives each heading an `id` if it hasn't got
one, builds the list, and injects it beside the body. Scroll-spy highlights the current section.
CSS turns `.shopify-policy__container` into a two-column grid on desktop with the nav `position:
sticky`, and collapses it into a `<details>` above the text on mobile.

- Keeps the canonical `/policies/...` URLs — which matters, because **the checkout footer links are
  generated by Shopify from Settings → Policies and cannot be repointed**. Customers arriving from
  checkout always land here. Any ToC has to exist on this route.
- One source of truth for the legal text. No copies to keep in sync.
- Works for all five policies at once, and for any policy added later.
- EN + SK for free: the headings come from whichever translation is rendering. Only the nav's own
  label ("On this page" / "Na tejto stránke") is a locale string.
- Costs: no-JS visitors get no ToC — they still get the whole policy, just without the sidebar, so
  nothing is lost that they had before. And we are restructuring DOM that belongs to Shopify, so a
  future change to `shopify-policy__*` markup could break the layout. Low risk, easy to spot.

Slugs should be generated from the heading text and **stable**, so `#legal-guarantee` and any future
hand-written anchor keeps working. Rule: use an existing `id` if present, otherwise slug the text.

### Option B — move the text to ordinary pages (`/pages/terms`)

Gives a real template, real sections, a server-rendered ToC and full theme-editor control. To avoid
a second copy of the legal text, the page would render `shop.terms_of_service.body` rather than a
pasted duplicate.

Rejected as the primary route: **checkout still links to `/policies/...`**, and those links cannot
be changed without a Checkout UI extension, which is Plus-level app work. So the policy URL stays
publicly reachable whatever we do, and it would be the version without the ToC — the worse
experience shown to the customer at the moment they are most likely to read it. Two URLs for the
same legal text is also exactly the duplication the legal work has been removing.

### Option C — nothing supported

There is no app block, section, metafield or template surface for policy pages. Confirmed: no
official insertion point exists.

## Recommendation

**Option A**, and split it into two pieces that can ship separately:

1. **Make policy pages look like the site.**

   > **Corrected 30 Sep 2026.** Adding `.t-policy` to the existing gate would change **nothing**.
   > Six of those seven rules match `.shopify-section` descendants, and a policy page has no
   > sections at all; the seventh matches `.page-width` / `.wui-wrap` / `.mw-inner` / `.fwi-inner`,
   > none of which exist in Shopify's policy markup. See `docs/design/UI-AUDIT-2026-09-30.md`.

   What actually has to happen: add `.shopify-policy__container` to the frame selector at
   `assets/walterin-ui.css:159` so the text takes `--wui-frame` / `--wui-frame-max` /
   `--wui-frame-pad`, and write new rules styling `.shopify-policy__title h1` as `wui-title` and
   `.shopify-policy__body .rte` as `wui-rte`. Today the only policy rule in the whole theme is
   `assets/base.css:664` (`padding-bottom: 3rem`) — there is no max-width and no horizontal padding
   at all, so the legal text runs to whatever width `<main>` gives it.
2. **Add the ToC.** New `snippets/policy-toc.liquid` plus a small script, rendered from
   `layout/theme.liquid` behind `{% if request.page_type == 'policy' %}`. Sticky two-column on
   desktop, `<details>` on mobile, `--wui-*` spacing, ink/paper/yellow only, current section marked
   with the yellow marker the accordions already use.

Do 1 first: if the pages are still laid out by Shopify's defaults, a sidebar will sit oddly
regardless.

## Open question for the lawyer/admin, not a blocker

Whether opening a policy in the **admin rich-text editor** and saving it strips API-written
markup — Shopify's editor is TinyMCE-based and sanitises on save. Our `id="legal-guarantee"` was
written through the API and has not yet survived a round-trip through the admin UI. Option A does
not depend on hand-written ids (it generates them), so this is a robustness note rather than a
risk to the plan — but if anyone edits a policy in admin, re-check that the anchor still works.

`class=`, `<div>` and `<nav>` in policy bodies were **not verified** — establishing that needs a
write. Option A needs none of them, which is another reason to prefer it.
